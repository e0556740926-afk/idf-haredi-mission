# אבני דרך

שבע אבני דרך. **אין מעבר לאבן דרך הבאה בלי שהקודמת עומדת ב-Definition of Done שלה במלואו.**
בסוף כל אבן דרך: `npm run lint && npm run test && npm run test:leak` ירוקים, commit, ודיווח קצר של מה נבנה ומה לא.

---

## M0 — תשתית
**מה:** ריפו, Vite+React+TS+Tailwind, RTL, Supabase CLI מקומי, מבנה מיגרציות, סקריפט seed, Vitest, Playwright, CI בסיסי.
אין עדיין אף טבלה ואף מסך — רק שהכול רץ.

**DoD**
- `npm run dev` מרים עמוד ריק בעברית עם `dir="rtl"`.
- `npx supabase start` + `npm run db:reset` רצים נקי.
- `npm run test` רץ עם בדיקה אחת מדומה שעוברת.
- CI מריץ lint + test על push.

---

## M1 — חוזה הנראות ⭐
**אבן הדרך החשובה ביותר בפרויקט.** כאן נקבע אם המוצר קיים.

**מה:**
- מיגרציות: `households`, `members`, `accounts`, `transactions`, `visibility_log`.
- פונקציות `current_member_id`, `effective_visibility`.
- RLS על כל הטבלאות.
- **ביטול grants** על טבלאות הבסיס.
- Views: `v_activity`, `v_allowance_summary`, `v_accounts_visible`, `v_accounts_existence`.
- `rpc_set_visibility` שכותב ל-`visibility_log`.
- Seed: משק בית אחד (דנה ויואב), 6 חשבונות, ~40 עסקאות חודשיות בשלוש רמות נראות — לפי הנתונים ב-`docs/05-seed-data.md`.
- **כל מטריצת הבדיקות ב-`docs/03-visibility-tests.md`.**

**DoD**
- כל בדיקות הדליפה עוברות.
- ניסיון `select * from transactions` מהקליינט בזהות יואב מחזיר **שגיאת הרשאה**, לא שורות מסוננות.
- `v_activity` בזהות דנה מחזיר 8 שורות; בזהות יואב — 5.
- `v_allowance_summary` בזהות יואב מחזיר שורה אחת עם `total = 1290` ו-`n = 3`, וללא אף עמודה מזהה.
- שינוי נראות דרך `rpc_set_visibility` נכשל כשהקורא אינו הבעלים.

**❗ אין להתחיל את M2 לפני ש-M1 ירוק לגמרי.**

---

## M2 — UI דק שמוכיח את המודל
כאן ה-UI מכוער בכוונה. המטרה היא לראות את הנתונים האמיתיים, לא לעצב.

**מה:** התחברות Supabase Auth, בחירת משק בית, מסך "פעילות" עם **מתג נקודת מבט** (החלפת משתמש מחוברת אמיתית, לא simulate), ומחוון נראות על כל שורה.

**DoD**
- התחברות כדנה → 8 שורות עם תווית "יואב רואה: …" בכל אחת.
- התחברות כיואב → 5 שורות + שורה מצטברת אחת "הכיס האישי של דנה — 1,290 ₪ · 3 פעולות" + שורת קיום חשבון פרטי.
- בשום מצב אין ברשת (Network tab) שדה `raw_description` או `merchant_id` של עסקה ששייכת לצד השני ב-`summary_only`. **זו בדיקה ידנית שחובה לבצע ולתעד.**

---

## M3 — ליבת הכסף
**מה:** קטגוריות + מנוע סיווג בארבע שכבות, תקציבי מעטפה, `rpc_safe_to_spend`, `rpc_cashflow`, זיהוי `recurring_series`, חיוב אשראי מרוכז ותשלומים, זיהוי העברות פנימיות.

**DoD**
- `rpc_safe_to_spend` מחזיר **אותו מספר בדיוק** לדנה וליואב.
- הפירוק שהפונקציה מחזירה מסתכם לסכום — בדיקה אוטומטית.
- סך ההוצאות החודשי תואם לשקל את ה-seed, **בלי ספירה כפולה** של חיוב האשראי המרוכז.
- התחזית ל-30 יום סוטה בפחות מ-8% מהידוע ב-seed.

---

## M4 — מנוע ההוגנות
**מה:** ארבעת הכללים, `rpc_settlement`, טבלת `settlements`, מסך "הבית".

**DoD**
- בכלל `income` על נתוני ה-seed: התוצאה **747 ₪ מיואב לדנה**, מאומת בבדיקה.
- החלפת כלל ל-`half` משנה את התוצאה ומתועדת ב-`rule_snapshot`.
- אין בשום מקום endpoint שמחזיר השוואה בין שני החברים.

---

## M5 — טקס הכסף
**מה:** `rituals`, `ritual_decisions`, בניית סדר יום אוטומטית, רישום החלטות, בדיקה אוטומטית של החלטות מהחודש הקודם, מונה רצף.

**DoD**
- סדר יום נבנה מנתונים אמיתיים (עליית מחיר, חריגת תקציב, יעד).
- החלטה שנרשמה עם `auto_check` נבדקת בהרצה הבאה ומסומנת בוצע/לא בוצע.

---

## M6 — קליטת נתונים
**מה:** `ProviderAdapter` interface + מימוש `ManualAdapter` ו-`CsvAdapter` בלבד. סנכרון אידמפוטנטי, `state` (pending/booked/removed), דה-דופליקציה לפי `fingerprint`, מודל `consent` עם `renewal_mode`.

**DoD**
- ייבוא אותו CSV פעמיים לא יוצר כפילויות.
- עסקה שעברה מ-`pending` ל-`booked` מתמזגת ולא מוכפלת.
- אין בקוד שום התייחסות ישירה לספק מסחרי — הכול דרך ה-interface.

**ספק אמיתי מתחבר רק אחרי M6, ורק מאחורי feature flag.**

---

## מה לא בונים עכשיו

AI וצ'אט, אוטומציות ו-WhatsApp, מנועי החיסכון, אפליקציה native, שווקים נוספים, תשלומים ומנויים.
כל אלה אחרי M6. אם נדרש מהם משהו — לשאול, לא לממש.
